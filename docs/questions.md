# Embedding 计划审查问题

审查对象：`docs/EMBEDDING_ITERATION_PLAN.md`。以下问题来自当前源码与计划的对照；“已纳入计划”不代表代码已经实现。
划线表示核心处理方案已确定，不代表相关代码已完成；未划线项仍有关键规则待确认。

## 优先级说明

- **P0**：影响基础搜索功能或索引正确性；进入对应代码实现前必须定下处理规则。
- **P1**：影响边界场景的召回、精度或故障降级；需纳入离线样本，并在扩大使用前验收。

## ~~1. [P0] 高级搜索的字面路如何评分和提取命中证据？~~

- **问题**：当前本地 `search_memory` 的字面评分和正文预览依赖 `query`。高级搜索不提供 `query`，所以硬过滤可能有效，但结果排序退化、命中正文证据也可能缺失。
- **影响**：满足 include AND 的候选无法按其与检索意图的相关程度排序；reranker 也可能看不到真正命中的正文。
- **方向**：普通 `query` 搜索能力从目标 API/工具中移除，不保留兼容入口。由 `terms.include` 派生内部 `include_text`；字面路用 include 词评分并定位命中，向量路用同一文本生成查询向量。
- **状态**：核心方案已确定并写入迭代计划；当前工作区源码仍有 query-only 分支，待后续实现移除。

## ~~2. [P0] 旧索引策略任务如何避免覆盖新索引？~~

- **问题**：同一记忆内容未变化时，旧分块策略任务可能晚于新策略任务完成。只校验源记忆版本仍会允许旧任务覆盖新索引。
- **影响**：数据库中留下旧策略块，而搜索只认当前索引版本，可能让该记忆暂时或持续不可检索。
- **已定方案**：每个 profile 持久化权威的当前目标 index_version。原子写入前锁定目标版本记录及记忆，持锁至提交，与版本切换互斥；同时校验源 revision/hash 和任务 index_version。不匹配就拒绝写入，不改动现有索引，也不把任务标成成功。
- **已定方案**：回填扫描根据源 revision 或 index_version 不匹配继续识别待处理记忆，并按当前目标版本重新生成；已有当前有效索引则无需重复生成，首版不单独增加重试队列。
- **状态**：设计问题已解决并写入迭代计划；代码实现待后续切片。

## ~~4. [P1] include 条件跨字段或多个 chunk 时，如何保留完整证据？~~

- **问题**：硬过滤作用于整条记忆，include 词可以分散在不同字段或正文块；若只保留少量最佳块，可能漏掉部分 include 命中依据。
- **影响**：候选虽正确满足 AND，reranker 却只看到部分依据，可能误判相关性并过滤掉目标记忆。
- **已定方案**：按记忆去重后，从各 include 的实际命中位置提取原文短上下文；保留对应字段内容、字段名与章节路径，合并重叠片段。每条记忆组装一份精简证据文本，对应一个 rerank document，得到一个重排分数；数据库负责完整的 AND 过滤，reranker 依据汇集的证据判断相关性。
- **已定方案**：取消“最多两个块”限制，按模型 token 预算组织证据；优先缩短外围上下文，保留各条件的命中依据。仍无法容纳完整依据时，按已定 rerank 降级规则处理，不提交缺少部分条件依据的证据文本；用跨字段、跨章节和预算不足样本验证。
- **状态**：设计问题已解决并同步迭代计划及检索字符画；代码实现和具体证据预算待后续切片与样本评测。

## ~~5. [P1] rerank 失败或响应不完整时，哪些候选可以返回？~~

- **问题**：provider 可能失败、返回空列表或只返回部分候选；当前实现会把未评分候选追加回结果，与“所有结果均经过相关性判断”的目标不符。
- **影响**：未评分的向量候选可能被误当成高置信结果；provider 故障也可能和正常的零相关结果混淆。
- **已定方案**：字面与向量候选合并后统一进入 rerank 阶段。rerank 失败、空响应或结果不完整时，只保留已通过字面路召回且满足全部硬条件的候选，不返回仅由向量路召回、未经相关性判断的结果；明确区分 provider 失败与成功但无相关结果。
- **待确认**：精确名称匹配在 rerank 故障时是否需要保留，以及部分返回响应应作为整体失败还是只丢弃未评分候选；用阶段 P0 样本固定。
